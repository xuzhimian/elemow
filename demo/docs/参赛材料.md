> 让你亲手派单、亲手催出超时，也亲手读到一句「还是放在门口就好」。

10 秒看懂版：

| | |
| --- | --- |
| 给谁 | 做配送调度 / 履约体验的人；也能被任何喜欢猫的人玩 |

## 五、有价值的反馈：用 AI 工具做地图应用的心得

这一节是我们最想交给主办方的部分——不是功能清单，而是**踩过的、值得被产品化的坑**。

### 1. 生成代码很快，但「物理世界的约束」必须靠人来兜底

模型能一次写对路径规划、图算法、UI 状态机；但坐标系这种**不在代码里、而在世界里**的事实，它给不出保证：
OSM 是 WGS-84，腾讯地图是 GCJ-02，国内有数百米系统性偏移。不转换，路网会整体「漂移」到隔壁街区。
正算之外还需要迭代反解（`gcj02ToWgs84`）来反推查询范围。

**建议**：地图类能力应该把「坐标系」作为一等公民暴露出来——SDK 层面提供显式标记与自动转换，而不是靠每个开发者自己知道。

### 2. SDK 的隐式行为，只能靠「跑起来看」获得

三个纯粹靠观察才能定位的行为：

- `boundary` 是 **cover 语义**（不许看到边界外），不是 contain。区域宽高比与容器不一致时，较长一边会被挤出可视范围——我们这里左右各溢出 357 px，`fitBounds` 的 padding 完全无效。
- `PolylineStyle` 在 `borderWidth: 0`，或线宽 ≤4 且带 `dashArray`／半透明时**整条线不绘制**，只能靠试出「宽度 ≥5 + `borderWidth: 1`」。
- SDK 会在容器内注入 `z-index: 1000` 的事件层，若祖先元素没有建立层叠上下文，它会逃逸到根层叠上下文，压过所有弹窗——曾导致全站按钮点击无响应。

**建议**：这类行为应当写进文档的「已知行为」小节，或提供 lint／运行时告警；纯靠调用方试错，成本极高。

### 3. 「看起来对」的验证最危险：假阴性

我做越界校验时写 `v.lng ?? v[0]`，但锚点实际结构是 `{ node: "79_-26" }`，读到 `undefined`，比较恒为 false，于是打印出漂亮的「越界 0 / 18」。真相是 **13 / 18 越界**。
同类问题第二次出现：脚本里的 `AREA_LOCAL` 只有 min/max、没有 `width`/`height`，新加的约束全部变成 `NaN` 比较而**静默失效**，表现为「丢弃越界节点 0」。

**建议**：给 AI 生成的数据校验代码加一层**结构断言**——先断言字段存在与量纲合理，再做业务判断。否则「校验通过」本身就是假信号。这一点值得做成通用能力。

### 4. 外部依赖不可靠时，预烘焙比在线抓取可靠

Overpass 公共镜像限流严重（429／504／SSL 失败反复出现），运行时抓取不可接受。
最终改成**预烘焙**：离线把路网与地点固化为随项目发布的 JSON（约 45 KB），运行时零网络依赖、每次启动结果一致；镜像可用时再走在线重烘焙。

**建议**：给地图类应用提供官方的「离线路网包」能力——给定区域导出可寻路数据，会比让所有人各自去撞公共镜像限流有效得多。

### 5. 降级要沿「语义优先级」走，而不是走到报错

我们的链条是：腾讯步行路线 → OSM 真实路网 → 示意网格 → 灰盒街区。
每一级都明确标注「你正在看的是什么、与真实道路差多少」，而不是抛一个空地图或错误弹窗。缺 Key 时直接进灰盒模式，玩法完整、离线可玩。

**建议**：把「降级可见性」做成 SDK 的通用能力——应用能一声调用拿到当前数据来源与可信度，并展示给用户。

### 6. 把设想落成可计算规则，是 AI 最擅长的部分

「地点命名要贴合真实环境」这类设想，落到实现是：**OSM 标签归类 → 路口周边加权投票 → 按稀缺度与最小间距做约束分配 → 词根加属性后缀生成名字**。
这一步模型完成得很好，包括权衡过程：收紧间距会让「独居老奶奶」落进餐饮区，于是引入 `strict` 标记让强人设地点优先挑位，最终「间距 165 m」与「强人设地点全部命中首选属性」兼得。

### 7. 工具链的实际摩擦

清理临时文件时的 `rm`／`pkill` 反复触发审批等待直至超时，拖慢了清理与回归节奏；批量截图验证也缺少一次性的归集与清理入口。
**建议**：为「本地验证」这类明确安全的动作提供免审批通道或批量清理能力。
